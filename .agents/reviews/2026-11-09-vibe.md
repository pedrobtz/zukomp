# zukomp review — findings

Review of the R package `zukomp` (byte compression via a pluggable codec
registry; vendored `miniz`, `zstd`, `lz4` under `src/vendor/`). Scope:
correctness bugs only — code that compiles and works on simple input but can
return wrong results, crash R, or corrupt memory. Style, performance and
documentation are out of scope.

Review method: full read of every file in `src/*.c` (R boundary, stream
driver, codecs, registry, gzip parser, frames prober), the R layer
(`R/*.R`), the vendored-patch set (`tools/patches/` applied into
`src/vendor/`), `src/Makevars`, `src/init.c`, `NAMESPACE`, and
`src/install.libs.R`. Registration entries were cross-checked one-by-one
against every `.Call` site in the R source.

Note: an earlier review exists at `review.md`. Findings M1 and M2 below
overlap with its high-priority items; both are independently re-derived
here from my own code-path analysis. Everything else is either new, or a
known-and-pinned deviation called out explicitly as such.

---

## M1. DEFLATE encoder silently truncates input larger than 2^31-1 bytes

**Severity:** wrong-result — silent, checksum-consistent data loss.
**Location:** `src/codec_deflate.c:395` (the input clamp), `:412` (flush
passthrough), `:451` (STREAM_END accepted without checking consumption).

In `deflate_process()`, the ST_BODY encoder clamps the input handed to
miniz to `0x7FFFFFFF` bytes:

```c
s->mz.avail_in = (unsigned int) ((avail_in > 0x7FFFFFFFu)
                                  ? 0x7FFFFFFFu : avail_in);
```

but the R flush is still translated to `MZ_FINISH` and passed through.
`ZU_FINISH` is only reached once in the R path — `zu_int_whole()` sets
`r.in_chunk = r.n`, i.e. the whole input is offered in one chunk — so when
`r.n >= 2147483648`, miniz receives the clamped `0x7FFFFFFF`-byte slice
together with `MZ_FINISH`, treats the slice as *the entire stream*,
emits the final block, and returns `MZ_STREAM_END`.

The wrapper then:

1. builds the trailer (gzip CRC-32 + ISIZE, or zlib Adler-32) from
   `s->checksum` / `s->uncompressed`, which were accumulated over `used`
   — the clamped slice only — so **the checksum is consistent with the
   truncated prefix**;
2. returns `ZU_STREAM_END` to the drive loop, which breaks and packages
   the output.

The remaining `n - 0x7FFFFFFF` input bytes are never offered, no error is
raised, and the compressed stream round-trips cleanly to the truncated
prefix. `out.consumed` reports the truth, but nothing — the driver, the
one-shot loop, or the R wrapper — checks it. Downstream integrity checking
cannot detect this: the gzip CRC matches the lossy output.

The same code path is reachable through the public C one-shot
`zu_compress_one()` for any consumer.

**Trigger (R):**

```r
x <- as.raw(rep(0x41, 2147483648))   # 2 GiB input
z <- komp_compress(x, "gzip")        # no error
identical(komp_decompress(z, "gzip"), x)   # FALSE: silently 2^31-1 bytes
length(komp_decompress(z, "gzip"))   # 2147483647, not 2147483648
```

Any of `"gzip"`, `"zlib"`, `"deflate-raw"` is affected. (An earlier
reviewer reproduced the same path natively: 2147483648 input bytes, status
`ZU_OK`, gzip ISIZE 2147483647.)

**Minimal fix (in `deflate_process()`, before calling miniz):**

```c
int mz_flush = zu_int_to_mz_flush(flush);
/* Input remains beyond the int-sized miniz slice, so this call is not
   the last of the stream: FINISH must not claim it is. */
if (s->encoder && avail_in > 0x7FFFFFFFu) {
    mz_flush = MZ_NO_FLUSH;
}
```

The final call (whose slice fits in `int`) then carries `MZ_FINISH`, and
the checksum/trailer accumulate over the full input as before. Add a
belt-and-braces invariant in `zu_int_one_shot()`: for `encode`, require
`buf.src_pos == buf.src_size` at `ZU_STREAM_END`, otherwise return
`ZU_ERR_INTERNAL`.

**How to verify:**

- Direct: `komp_compress` of a 2^31-byte input, count
  `length(komp_decompress(...))` — must equal 2^31 after the fix; before
  the fix it is 2^31-1 with status success.
- Cheap CI variant that avoids allocating 2 GiB: drive the encoder with a
  hand-fed `zu_buffer` whose `src_size` is deliberately set above
  `0x7FFFFFFF` (or shrink the clamp behind a test-only macro). Assert
  `STREAM_END` is only ever returned with `src_pos == src_size`.
- Boundary sweep around `n = 2147483645..2147483650` through
  `zu_compress_one()` (native) to catch the off-by-clamp edge.

**Confidence:** high (full code-path analysis; matches an independent
reproduction recorded in `review.md`).

## M2. `zu_register_codec()` dereferences a short vtable before validating `struct_size`

**Severity:** memory-safety (out-of-bounds read) on the public C ABI.
**Location:** `src/zu_registry.c:94` (reads `vtable->name`, `vtable->source`)
before `:108` (the `struct_size` check).

The current order is:

```c
if (vtable == NULL || vtable->name == NULL || vtable->source == NULL) {
    return ZU_ERR_INVALID_ARGUMENT;
}
...
if (vtable->struct_size < ZU_VTABLE_REQUIRED_SIZE) {
    return ZU_ERR_INVALID_ARGUMENT;
}
```

`name` lives at offset 8 and `source` at offset 40 of `zu_codec_vtable`,
but `struct_size` (offset 0) — the only field a short allocation is
guaranteed to contain — is checked *after* both pointers are read. The
struct_size forward-compatibility contract in `zukomp.h` exists precisely
so that a vtable compiled against an older (shorter) header can be
*rejected* cleanly; instead, a satellite registering a genuinely short
allocation (e.g. `malloc(4)` holding only the size field) causes an
out-of-bounds read of up to ~40 bytes past the allocation.

This is the C-callable registration surface (`zu_register_codec` in the
API table reached through `R_GetCCallable`), i.e. reachable from any
downstream package at DLL-load time, not from R itself.

**Trigger (C, from a satellite package):**

```c
unsigned char *short_vtable = malloc(4);
memcpy(short_vtable, &(uint32_t){4}, 4);        /* struct_size = 4 */
zu_get_api(1)->register_codec((zu_codec_vtable *) short_vtable);
/* ASan: heap-buffer-overflow read at offset 8, instead of a clean
   ZU_ERR_INVALID_ARGUMENT */
```

**Minimal fix — reorder the checks:**

```c
if (vtable == NULL) { return ZU_ERR_INVALID_ARGUMENT; }
if (vtable->struct_size < ZU_VTABLE_REQUIRED_SIZE) {
    return ZU_ERR_INVALID_ARGUMENT;
}
if (vtable->name == NULL || vtable->source == NULL) {
    return ZU_ERR_INVALID_ARGUMENT;
}
```

Note the mirror-image gap is already handled correctly elsewhere in the
codebase (`zu_int_copy_opts()` copies only `min(struct_size, sizeof)`),
which makes this the one place the contract is violated.

**How to verify:** ASan-instrumented test in the consumer test package
registering a real `malloc(4)` allocation. The existing test suite only
lies about `struct_size` of a full-size vtable, which cannot trigger the
OOB — it must be an actual short allocation. Before the fix: ASan report;
after: `ZU_ERR_INVALID_ARGUMENT` with no diagnostic.

**Confidence:** high (static; validation order is unambiguous).

## M3. Structurally invalid DEFLATE is classified depending on chunking (output limit vs invalid data)

**Severity:** wrong-result (error class); robustness for an HTTP-client
consumer.
**Location:** `src/codec_deflate.c:519-540` (the no-progress/stall
classification), interacting with miniz's tinfl lacking structural
end-of-block validation on the streaming path. Partially mitigated by the
vendored distance-validation patch (`miniz.c:2805`), which closes the
invalid-distance half of this but not the end-of-block half.

miniz's tinfl does not validate the presence of the end-of-block code the
way zlib does (zlib's inflate explicitly rejects the missing-EOB case). A
stream with a missing end-of-block marker (the `raw-missing-end-of-block`
fixture) is therefore interpreted as an unbounded run of matches:

- fed **whole** at once, miniz fails early and the wrapper rejects it as
  `ZU_ERR_INVALID_DATA` with zero output;
- fed **one byte at a time** (as a socket would), the same bytes produce
  thousands of garbage output bytes and are stopped only by the
  `max_output` cap, surfacing as `ZU_ERR_OUTPUT_LIMIT`.

So the condition a caller branches on is a function of *delivery*, not of
the data. (`test-malformed.R:70` pins this as an accepted deviation with a
manifest note; it stays in this list because the observable contract —
error class — is genuinely delivery-dependent, and a caller that treats
`zukomp_output_limit` as "retry with a bigger cap" will decode unbounded
garbage instead of getting a structural rejection.)

**Trigger (R, using the fixture + harness):**

```r
x <- malformed_bytes("raw-missing-end-of-block")   # 36-byte fixture
komp_decompress(x, "deflate-raw", max_output = 8192)
# -> zukomp_invalid_data  (whole input)
zu_test_stream(x, "deflate-raw", "decode", in_chunk = 1L,
               out_chunk = 1L, max_output = 8192)
# -> zukomp_output_limit  (~8 KiB garbage produced first; same bytes)
```

**Minimal fix:** classification-level: in `deflate_process()`'s ST_BODY
decoder, when `flush == ZU_FINISH`, all input is consumed, miniz reports
`MZ_BUF_ERROR`/no-progress and the stream never reached `MZ_STREAM_END`,
map to `ZU_ERR_INVALID_DATA` rather than letting the driver's output-cap
check win the classification race. The full fix belongs in miniz
(an upstreamable EOB-presence check, analogous to the 0002 match-distance
patch), plus a regression that pins the class across chunk sizes 1..n
at a small output budget.

**How to verify:** sweep `in_chunk = 1..length(x)` on the fixture at a
small `max_output` and assert a single condition class
(`zukomp_invalid_data`) for every chunk size; output bytes must be
`raw(0)` in all cases. Compare against zlib/gzip CLI behaviour on the
same fixture (rejects as invalid compressed data).

**Confidence:** medium-high for the misclassification mechanism (pinned in
the project's own manifest and an earlier reproduction; the ~8 KiB figure
comes from the recorded manifest note, not re-measured in this review).

## M4. Stream-handle ownership gap between allocation and extptr registration

**Severity:** robustness (memory leak only; no crash).
**Location:** `src/zu_whole.c:172`/`:182` (`zu_encoder_new` /
`zu_decoder_new` succeed and return a calloc'd handle) vs `:189` (the
`R_MakeExternalPtr` + `R_RegisterCFinalizerEx` that establishes the
finalizer).

If `R_MakeExternalPtr()` fails to allocate it raises an R error and
longjmps past the function's cleanup; at that instant the native handle
(the `zu_encoder`/`zu_decoder` struct and everything its `_new` allocated —
miniz's malloc'd dictionary, ZSTD CCtx/DCtx, LZ4F contexts) has no owner:
the finalizer that protects the interrupt longjmp in the drive loop below
does not exist yet, and the `free()`s in this function are never reached.
Raw `calloc` memory is invisible to the GC, so it leaks permanently.

This is precisely the design-13 invariant ("owned by an external pointer
for as long as it exists") being established one statement too late. The
same file already demonstrates the correct idiom for the *output sink*:
`zu_int_outbuf_owner()` creates and registers the null extptr first, and
`zu_int_reserve()` calls `R_SetExternalPtrAddr` only afterwards.

**Trigger:** R allocation failure at the `R_MakeExternalPtr` call site —
not naturally reproducible without fault injection (gctorture alone does
not deterministically hit an alloc failure at that instruction, and the
allocation is tiny).

**Minimal fix:**

```c
SEXP guard = PROTECT(R_MakeExternalPtr(NULL, R_NilValue, R_NilValue));
R_RegisterCFinalizerEx(guard, r->encode ? zu_int_encoder_finalizer
                                        : zu_int_decoder_finalizer, TRUE);
st = r->encode ? zu_encoder_new(&enc, &opts) : zu_decoder_new(&dec, &opts);
if (st != ZU_OK) { UNPROTECT(1); return st; }
R_SetExternalPtrAddr(guard, r->encode ? (void *) enc : (void *) dec);
```

**How to verify:** allocation-failure injection in a debug build (fail the
Nth R allocation for increasing N until the `R_MakeExternalPtr` one is
hit); assert via ASan/LeakSanitizer that zero bytes leak where the
unpatched build shows one `zu_encoder` plus codec-internal allocations per
injection.

**Confidence:** high by inspection; observation requires injection.

## M5. Frame-continuation lookahead consumes bytes it cannot return (known deviation; native-consumer contract issue)

**Severity:** wrong-result for native consumers (`zu_decoder_process`
users); robustness in R. **Known and documented** in the file header and
pinned by `test-members.R`; kept in the findings because the loss affects
the package's stated network-resumption use case.
**Location:** `src/zu_frames.c:114` (`memcpy(f->held, p, k);
buf->src_pos += k;`) plus the disproof paths at `:131-147`; the gzip
equivalent is the `probe_magic` hold in `codec_deflate.c` ST_MEMBER_END.

When a zstd/lz4 frame ends and the following bytes *might* be the start of
another frame's magic (`28 b5 2f fd` / `04 22 4d 18`, one to three bytes
visible), the prober consumes them into `f->held` so the drive loop
refills. If a later byte disproves the prefix, the held bytes are
discarded but stay counted as consumed: `src_pos` (and therefore
`out.consumed`) can run up to three bytes past the true end of the
stream. Gzip has the two-byte analogue with its `probe_magic` hold.

- The R-level wrapper is unaffected: the tail triggers the trailing policy
  even from the held state, so `komp_decompress()` answers correctly in
  both cases.
- A **native consumer** that resumes reading the next message from the
  reported cursor (the keep-alive HTTP connection case) silently loses up
  to three bytes of the following message.

**Trigger (C):** construct a zstd frame followed by a tail beginning with
a partial magic (`28 b5` or `28 b5 2f`), delivered so the tail straddles a
process() input boundary, and decode; then compare the reported consumed
count with the true frame length. Example shape:

```c
/* frame || 28 b5 00, the tail split across two process() calls */
st = zu_decoder_process(d, &buf, ZU_FINISH);
/* consumed reports 3 bytes past the frame end; the two "28 b5" bytes
   cannot be returned to the caller */
```

**Minimal fix:** none exists that does not change the streaming contract;
the honest options are (a) a holdback out-param (a "pending prefix"
returned to the caller on `ZU_STREAM_END`), or (b) an explicit
API-level statement that `src_pos` is exact except within three bytes of
a frame end at a chunk boundary, so connection-resumption consumers know
to re-deliver the tail. Do not refactor silently — chunk-size invariance
is asserted by sweeps that pin the current behaviour.

**How to verify:** in the C consumer package, drive `frame ||
tail-prefix` at every in/out chunk size and assert the consumed-bytes
bookkeeping is either exact or bounded by +3 and documented as such.

**Confidence:** high for the mechanism (it is what the file's own comment
says); whether a concrete consumer is harmed depends on that consumer's
parsing strategy.

## M6. Vendored miniz patch: match-distance history accumulates unclamped in `size_t` (32-bit build)

**Severity:** portability.
**Location:** the local patch
`tools/patches/miniz/0002-validate-match-distance.patch`, applied at
`src/vendor/miniz/miniz.c:2923` (`r->m_total_out += ...`) and the field at
`miniz.h:1056`.

The patch adds `m_total_out` to tinfl so match distances can be bounded by
"bytes ever emitted since `tinfl_init()`" rather than by position in a
wrapping output buffer. This is correct on 64-bit, and the 64-bit
semantics were verified thoroughly:

- wrapping mode caps the check at `out_buf_size_mask + 1` = 32 KiB, which
  matches RFC 1951's maximum distance (32768), so no valid stream is
  rejected;
- reserved distance codes 30/31 fall in at the `dist == 0` rejection;
- the counter is reset by `tinfl_init()` and therefore by
  `mz_inflateReset()`;
- for the NON_WRAPPING path miniz's own `mz_inflate` first-call
  MZ_FINISH fast line, the new check is equivalent to the one it replaced
  — and zukomp's decoder never reaches that fast line anyway, because
  `codec_deflate.c` rewrites a first-call `MZ_FINISH` to `MZ_SYNC_FLUSH`.

The one weakness: on an ILP32 (32-bit) build, `m_total_out` is a 32-bit
`size_t` and cannot saturate; it *wraps*. Wrapping shrinks `total_out`,
after which the `dist > MZ_MIN(total_out, window)` check can (a)
spuriously reject valid matches after ~4 GiB of cumulative output through
one tinfl stream, misclassifying valid data as `ZU_ERR_INVALID_DATA`,
or (b) within the wrap window, under-validate a match distance.
Reachability is low — 32-bit R cannot hold the buffers, so only a C
consumer streaming >4 GiB through multiple `zu_decoder_process` calls on
a 32-bit process is exposed — but the stated invariant in the patch
comment ("saturating is not needed") is false for 32-bit.

**Trigger (32-bit build, C):** a decompression loop whose cumulative output
crosses 2^32 bytes across many calls (e.g. a large stored-block stream fed
in small pieces); after the wrap, valid matches near the original total
can be rejected.

**Minimal fix — clamp at accumulation time, against the window it is only
ever `MZ_MIN`-ed against:**

```c
r->m_total_out += (size_t)(pOut_buf_cur - pOut_buf_next);
```

becomes, for the wrapping case:

```c
r->m_total_out = MZ_MIN(r->m_total_out + (size_t)(pOut_buf_cur - pOut_buf_next),
                        out_buf_size_mask + 1);
```

**How to verify:** a 32-bit CI build (`-m32` or an i386 container) driving
more than 4 GiB cumulative output through a held `tinfl` stream in unit
chunks, asserting a valid stored-block loop still decodes correctly after
successive window crossings.

**Confidence:** low-medium ("possible — verify on a 32-bit build"); the
64-bit behaviour is verified clean.

## Ranking: the five most severe findings

1. **M1 — DEFLATE silent truncation at 2^31-1.** Silent,
   checksum-consistent data loss directly reachable from
   `komp_compress()`; the worst kind of wrong result because nothing
   downstream can detect it.
2. **M2 — `zu_register_codec()` OOB read on a short vtable.** Memory
   safety on the public C surface, reachable by any satellite package at
   DLL-load time.
3. **M3 — Chunking-dependent error class for invalid DEFLATE.** An
   output-limit failure as a facade over an invalid stream is
   attack-surface (a caller that raises the cap decodes unbounded
   garbage), not just a UX wart.
4. **M5 — Frame-lookahead byte consumption.** The zukomp-to-connection
   resume contract can lose up to three user bytes; known and pinned by
   tests, but it is a real contract break for the stated network-consumer
   use case.
5. **M4 — Guard-creation order leak window.** Low probability (requires
   an R allocation failure at one specific small allocation), but the fix
   mirrors an idiom already in the same file.

M6 (32-bit `m_total_out` wrap) sits below these five: it needs an ILP32
build plus >4 GiB through one stream, and is flagged "possible — verify".

## Areas checked and found clean

- **SEXP contracts, live R surface:** all five exported functions plus the
  internal test harness; type, length, NA, Inf and narrowing all handled
  before C is reached.
- **PROTECT balance on every normal and error path;** extptr finalizers
  protect all interrupt/longjmp paths in the drive loop (the one gap is
  M4).
- **NA/NaN/Inf:** every boundary value goes through the checked
  narrowing helpers; no float-cast-overflow paths survive from R; no
  bitwise double comparisons anywhere.
- **Integer/size overflow:** every buffer computation routes through
  `zu_buf.c`'s checked add/mul/grow; no bare size arithmetic anywhere
  else (the one `int` boundary in the package is M1).
- **Registration vs NAMESPACE:** all 24 `R_CallMethodDef` entries were
  compared one-for-one with `.Call` sites in `R/`; useDynLib
  `.registration = TRUE` + `R_useDynamicSymbols(FALSE)` +
  `R_forceSymbols(TRUE)` are consistent. Makevars suppresses no
  warnings, does not override `$(CFLAGS)`/`$(LDFLAGS)`, and the
  per-object xxHash namespacing is per-translation-unit consistent.
- **R layer validation:** type, length, NA, Inf-the-alias-for-no-limit,
  fractional rejection before narrowing, and level-range checks against
  the live codec table all happen before `.Call`.
- **Vendored patches reviewed:** miniz 0002's 64-bit semantics and
  header-Finish fast-path interplay are sound (verified above; 32-bit
  caveat is M6); miniz 0001/0003 and the zstd/lz4 pragma/assert guards
  are hygiene only.
- **Verified correct as well:** the gzip member probe handling of a
  `1f 00` tail, zlib FCHECK/FDICT handling, `mz_inflateReset` resetting
  `m_has_flushed`, lz4f staging-buffer sizing under upstream
  `LZF_compressBound`'s buffered-input semantics, zstd windowLogMax
  clamping, the lz4-block size-search loop, and the registry's
  duplicate-name/token rejection.

## Suggested harness additions (edge-case inputs to keep pinned)

- `komp_compress(raw(0 / 1 / 2^31-1 / 2^31 / 2^31+1), c)` for every
  DEFLATE-family codec (M1; use a compressible pattern to keep memory
  feasible).
- All-NA/NaN/Inf limit vectors: `max_output = c(1, NA)`, `NaN`, `Inf`,
  `-Inf`, `0.5`; `max_ratio` idem; `level = c(1, NA)` — assert condition
  *classes*, not just "errors".
- Zero-length sources: `komp_compress(raw(0), c)` and
  `komp_detect(raw(0) / raw(1))` on every codec.
- Delivery-boundary splits: two gzip members with `1f 8b` straddling
  every possible boundary; zstd split inside the 4-byte magic; `28 b5 2f`
  tails; `1f` alone at source end (the `1f 00` tail regression — keep
  pinned); XLEN = 0 / 1 / 65536; FNAME/FCOMMENT split at every byte;
  FHCRC wrong at position 1 vs 2.
- Silent-coercion traps: `max_output = "1024"`, `codec = 1`,
  `level = "6"` vs `6L`, `x = list()` — every one should raise
  `zukomp_invalid_argument` before reaching C.
- `komp_detect` on an FDICT zlib stream: must answer "zlib", and
  `komp_decompress` must raise `zukomp_unsupported_codec` (not
  invalid-data).
- Fixture-class sweeps: decode every `fixtures/malformed` vector at every
  chunk size and assert one class per vector (M3).
- 32-bit wrap case (M6): map the >4 GiB cumulative-output case into a
  `tinfl` loopback test behind an `#if SIZE_MAX < UINT64_MAX` test-only
  build.
